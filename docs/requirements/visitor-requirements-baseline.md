- 把“访客已经登记”解释成“访客已经获准通行”；
- 因为采用微服务而把一个业务角色拆成多个前端系统；
- 让前端隐藏字段代替后端数据权限控制；
- 在待确认事项没有结论时自行选择业务规则；
- 在第一阶段直接建设未确认需要的复杂服务。

## 2. 项目目标、范围与边界

### 2.1 项目目标（已确认）

建设一套厂区访客管理平台，实现：

```text
二维码访客登记
→ 数据分别提供给门卫和宿舍
→ 门卫手动记录入厂
→ 宿舍处理住宿和床位
→ 门卫手动记录离场
→ 总后台统一查询
```

访客预约流程为：

```text
OA流程领导审批（必须）
+
电话通知（可选）
```

每次预约都必须进入 OA审批流程；电话通知是可勾选的附加项，不是必选项，也不能替代 OA审批。

### 2.2 当前现实业务（已确认）

- 访客当前依赖二维码登记及人工处理；
- 门卫负责访客进厂和离场的人工确认记录；
- 宿舍负责住宿确认及床位调整；
- 门卫接收并查看 OA 审批结果；
- OA审批结果只作为门卫查看的信息，不作为系统禁止确认入厂的条件；
- 即使 OA审批结果为“已驳回”，门卫仍可以手动点击确认入厂；
- 门卫不接收电话通知过程和结果；
- 门卫页面展示访客登记记录和 OA审批结果；门卫不执行或修改审批。

### 2.3 第一版范围（已确认与建议组合）

第一版至少包括：

- 二维码公开登记页；
- 登记后必须触发 OA 审批流程；勾选电话通知时才处理电话通知；
- 门卫访客记录页面；
- 门卫手动确认入厂、离场；
- 宿舍访客页面；
- 宿舍住宿确认、床位安排和调整；
- 统一登录、角色与权限；
- 总后台综合查询；
- 操作日志；
- 作为子应用接入企业统一网站的能力。

### 2.4 当前门卫记录边界（已确认）

- 当前门卫仍然手动记录访客入厂和离场；
- 闸门由门卫自行控制，不属于本项目开发范围；
- 本项目不开发闸门控制、自动开闸或远程开闸功能。

## 3. 角色与最终系统呈现

### 3.1 角色

| 角色编码 | 角色 | 主要职责 |
|---|---|---|
| `VISITOR` | 外部访客 | 扫码并填写来访信息 |
| `GUARD` | 门卫 | 查看限定字段，确认入厂和离场 |
| `DORM_ADMIN` | 宿舍管理员 | 查看登记信息，确认住宿及调整床位 |
| `ADMIN` | 后台/行政管理员 | 综合查询登记、进出和住宿数据 |
| `SYSTEM_ADMIN` | 系统管理员 | 用户、角色、权限和系统配置 |

### 3.2 最终呈现方式（已确认）

系统整体是一套统一 Web 管理系统：

- 一个统一域名和内部登录入口；
- 登录后按角色展示不同菜单和页面；
- 首页卡片用于数据概览和快捷进入模块；
- 卡片进入的是同一系统中的业务模块，不是打开互相割裂的网站；
- 二维码登记页是公开入口，不显示后台菜单；
- 后端即使拆成多个微服务，用户仍只感知一套系统。

建议路由：

```text
/visitor/register        二维码公开登记页
/visitor/login           内部登录页
/visitor/dashboard       首页总览
/visitor/guard           门卫工作台
/visitor/dormitory       宿舍工作台
/visitor/registrations   登记查询
/visitor/reports         综合查询与报表
/visitor/system          用户、角色和权限
```

## 4. 二维码登记需求

### 4.1 登记字段（已确认）

| 字段 | 必填规则 | 说明 |
|---|---|---|
| 姓名 | 必填 | 访客姓名 |
| 手机号 | 必填 | 访客联系方式 |
| 被访人 | 必填 | 内部被访人员 |
| 被访部门 | 必填 | 内部部门 |
| 来访事由 | 必填 | 来访事件/事项 |
| 是否住宿 | 必填 | 是/否 |
| 是否有车辆 | 必填 | 是/否 |
| 车牌号 | 条件必填 | 有车辆时填写 |
| 是否开车进厂 | 必填 | 开车到厂不等于车辆进入厂区 |
| 是否需要电话通知 | 可选 | 勾选后处理电话通知；不影响 OA审批必走 |
| 登记时间 | 系统生成 | 使用服务器时间 |
| `visit_id` | 系统生成 | 一次来访唯一编号 |

### 4.2 数据分发（已确认）

二维码登记成功后：

- 门卫获得规定的部分字段；
- 宿舍获得二维码登记的完整业务数据；
- 每次登记必须进入 OA 审批流程；
- 只有勾选电话通知时才进入电话通知处理；
- 电话通知不能替代 OA审批；
- 门卫接收并查看 OA审批结果，但不接收电话通知结果。

| 字段 | 门卫 | 宿舍 | 后台管理员 |
|---|---:|---:|---:|
| 姓名 | 可见 | 可见 | 可见 |
| 手机号 | 可见 | 可见 | 可见 |
| 身份证号 | 不返回 | 业务完整数据，展示方式待确认 | 按权限 |
| 被访人 | 可见 | 可见 | 可见 |
| 被访部门 | 不返回 | 可见 | 可见 |
| 来访事由 | 不返回 | 可见 | 可见 |
| 是否住宿 | 不返回 | 可见 | 可见 |
| 是否有车辆 | 待确认是否展示 | 可见 | 可见 |
| 车牌号 | 可见 | 可见 | 可见 |
| 是否开车进厂 | 可见 | 可见 | 可见 |
| OA审批/电话通知处理信息 | 不返回 | 依据权限 | 可见 |
| OA审批状态/结果 | 可见、不可修改 | 待确认 | 接入后按权限 |
| 电话通知状态/结果 | 不返回 | 待确认 | 按最终规则 |

- 明文查看、脱敏和审计方式待业务确认；
- 服务只获取完成自身职责所需的最少字段。

## 6. 状态模型

不同业务状态必须分开保存，禁止使用一个超大状态字段表达所有组合。

### 6.1 登记状态

```text
REGISTERED  已登记
CANCELLED   已撤销
EXPIRED     已过期
```

撤销、过期规则待确认。

### 6.2 预约处理状态

OA审批是每次预约的必走流程。电话通知是可选附加流程，只有登记时勾选才创建电话通知状态。

OA 分支建议状态：

```text
NOT_STARTED → PROCESSING → APPROVED / REJECTED / FAILED
```

电话通知分支状态取决于最终模式：

- 人工电话：`PENDING → COMPLETED / FAILED`；
- 自动电话：`QUEUED → CALLING → ANSWERED / UNANSWERED / FAILED`。

在电话模式未确认前，不得固定实现。

### 6.3 门卫进出状态（已确认）

```text
WAITING_ENTRY → IN_FACTORY → EXITED
```

| 当前状态 | 操作 | 下一状态 | 记录内容 |
|---|---|---|---|
| `WAITING_ENTRY` | 门卫点击确认入厂 | `IN_FACTORY` | 服务器入厂时间、操作人 |
| `IN_FACTORY` | 门卫点击确认离场 | `EXITED` | 服务器离场时间、操作人 |

确认入厂的状态前置条件：

```text
guard_status = WAITING_ENTRY
```

OA审批状态不作为入厂接口的拦截条件。门卫点击确认入厂后，系统使用服务器当前时间记录入厂时间。

### 6.4 宿舍状态（建议，待业务确认）

```text
NOT_REQUIRED
PENDING_CONFIRMATION
PENDING_BED
BED_ASSIGNED
CHECKED_IN
CHECKED_OUT
```

## 8. 总体技术框架

### 8.1 架构原则

- 统一前端，后端微服务；
- 所有内部 API 经过 API 网关；
- 每个微服务拥有自己的数据边界；
- 使用 `visit_id` 贯穿登记、门卫、宿舍、OA、通知和查询；
- 同步 API 用于立即查询；
- 消息事件用于登记后的跨服务分发；
- 消息中不传播身份证等敏感完整数据；
- 外部系统通过集成服务隔离；
- 初期可在一台应用服务器使用 Docker Compose 部署；
- 采用微服务不等于每个服务必须独占一台服务器；
- 第一版不要求 Kubernetes，后续多节点高可用时再引入。

### 8.2 推荐技术栈

| 层级 | 建议技术 |
|---|---|
| 前端 | Vue 3 或 React，统一管理端 + 二维码 H5 |
| 外部入口 | Nginx |
| API网关 | Spring Cloud Gateway |
| 后端服务 | Java + Spring Boot |
| 认证权限 | Spring Security 或 Sa-Token，最终服从企业统一认证 |
| 注册配置 | Nacos（服务数量和部署方式需要时启用） |
| 数据库 | PostgreSQL 或 MySQL |
| 缓存 | Redis（按实际需要） |
| 消息队列 | RabbitMQ/RocketMQ（登记分发需要可靠异步时启用） |
| 数据迁移 | Flyway/Liquibase |
| API文档 | OpenAPI/Swagger |
| 日志追踪 | 结构化日志 + `trace_id` |
| 部署 | Docker Compose；后期可迁移 Kubernetes |

### 8.3 逻辑架构

```text
访客二维码 / 内部用户
        ↓
      Nginx
        ├── /visitor/**       → 统一前端
        └── /api/visitor/**   → API Gateway
                                  ├── auth-service
                                  ├── visitor-registration-service
                                  ├── guard-record-service
                                  ├── dormitory-service
                                  ├── oa-integration-service
                                  └── admin-query-service
```

## 9. 微服务划分与职责

### 9.1 `api-gateway`

非业务服务，负责：

- 统一路由；
- Token 初检；
- 接口访问控制；
- 限流；
- 请求日志和 `trace_id`；
- 统一错误格式。

### 9.2 `auth-service`

负责：

- 内部用户登录；
- 用户、角色和菜单权限；
- API权限；
- 字段权限策略；
- 企业统一登录/组织架构对接。

不负责访客业务数据。

### 9.3 `visitor-registration-service`

主数据服务，负责：

- 二维码登记；
- 完整原始登记数据；
- 生成 `visit_id`；
- 登记查询、撤销、过期（后两项规则待确认）；
- 登记后必须触发 OA审批；
- 处理可选电话通知模块；
- 保存是否勾选电话通知及其处理状态（具体状态范围待确认）；
- 向不同服务提供最小权限视图；
- 发布 `VISITOR_REGISTERED` 事件。

建议内部只读接口：

```text
GET /internal/registrations/{visitId}/guard-view
GET /internal/registrations/{visitId}/dormitory-view
GET /internal/registrations/{visitId}/oa-view
```

### 9.4 `guard-record-service`

负责：

- 门卫访客列表；
- 门卫限定字段查询；
- 待入厂、当前在厂、已离场列表；
- 手动确认入厂；
- 手动确认离场；
- 确认入厂时展示但不拦截 OA审批状态；
- 进出时间和操作人审计；
- 管理员修正入口（规则待确认）。

不负责：

- OA审批；
- 电话通知；
- 修改OA审批结果；
- 宿舍床位；
- 闸门控制、自动开闸或远程开闸。

### 9.5 `dormitory-service`

负责：

- 接收/查询登记完整业务数据；
- 住宿需求处理；
- 宿舍楼、房间、床位；
- 床位确认和调整；
- 入住、退宿（是否纳入第一版最终以业务确认为准）；
- 当前住宿和历史记录；
- 操作审计。

### 9.6 `oa-integration-service`

负责：

- 每次预约登记后对接现有 OA；
- 发起流程、保存流程编号；
- 查询或接收流程结果；
- 接口失败重试；
- OA字段映射和调用日志。

OA审批结果需要同步给门卫记录服务用于展示；门卫只能查看，不能处理或修改审批结果。

### 9.7 `admin-query-service`

负责：

- 总后台首页；
- 登记、门卫进出和宿舍数据的综合查询；
- 当前在厂、当前住宿；
- 历史查询和报表；
- 跨服务只读视图；
- 操作日志统一查询。

不直接修改其他服务业务表。

## 10. 服务间数据流

### 10.1 登记主链路

```text
访客扫码提交
→ visitor-registration-service 保存完整登记
→ 生成 visit_id
→ 发布 VISITOR_REGISTERED
```

消费者：

```text
guard-record-service
→ 通过 guard-view 获取门卫字段
→ 创建 WAITING_ENTRY 记录

dormitory-service
→ 通过 dormitory-view 获取授权数据
→ 创建住宿处理记录

oa-integration-service
→ 每次登记后处理 OA 审批流程
→ 审批状态变化后发布 OA_APPROVAL_UPDATED
→ guard-record-service 接收并更新门卫可见的审批状态

visitor-registration-service 电话通知模块
→ 仅当登记时勾选电话通知才创建并处理电话通知任务

admin-query-service
→ 更新综合查询视图
```

### 10.2 门卫进出链路

```text
门卫查询记录
→ 点击确认入厂
→ guard-record-service 校验当前状态
→ 使用服务器时间写入 entry_time
→ 发布 VISITOR_ENTERED

访客离场
→ 门卫点击确认离场
→ guard-record-service 校验当前状态
→ 使用服务器时间写入 exit_time
→ 发布 VISITOR_EXITED
```

### 10.3 宿舍链路

```text
收到登记
→ 判断/确认住宿业务
→ 确认原床位或调整床位
→ 保存操作人、时间、前后床位
→ 后续按确认范围处理入住和退宿
```

### 10.4 消息事件最小字段

普通事件只包含：

```json
{
  "eventId": "EVENT-...",
  "eventType": "VISITOR_REGISTERED",
  "visitId": "VISIT-...",
  "occurredAt": "服务器时间",
  "version": 1
}
```

完整身份证、完整登记表不得直接放入普通消息事件。

### 10.5 一致性要求

- 事件必须有唯一 `eventId`；
- 消费者必须幂等；
- 本地事务和事件发布建议使用 Outbox；
- 消费失败需要重试和死信记录；
- 跨服务不使用普通数据库事务；
- 不允许服务直接修改其他服务的数据表。

## 11. API初步契约

### 11.1 公共登记

```text
POST /api/visitor/registrations
GET  /api/visitor/registrations/{visitId}/result
```

### 11.2 门卫

```text
GET  /api/visitor/guard/records?status=WAITING_ENTRY
GET  /api/visitor/guard/records?status=IN_FACTORY
GET  /api/visitor/guard/records/{visitId}
POST /api/visitor/guard/records/{visitId}/entry
POST /api/visitor/guard/records/{visitId}/exit
```

`entry`和`exit`接口不得接受客户端提供的实际时间作为正常路径；由服务器生成。

`entry`接口只校验门卫记录是否处于可入厂状态，不以 OA审批状态作为拒绝条件。即使 OA状态为 `REJECTED`，门卫手动确认后也应创建入厂记录并使用服务器时间。

### 11.3 宿舍

```text
GET  /api/visitor/dormitory/records
GET  /api/visitor/dormitory/records/{visitId}
POST /api/visitor/dormitory/records/{visitId}/confirm
POST /api/visitor/dormitory/records/{visitId}/assign-bed
POST /api/visitor/dormitory/records/{visitId}/change-bed
POST /api/visitor/dormitory/records/{visitId}/check-in
POST /api/visitor/dormitory/records/{visitId}/check-out
```

### 11.4 管理后台

```text
GET /api/visitor/admin/dashboard
GET /api/visitor/admin/registrations
GET /api/visitor/admin/guard-records
GET /api/visitor/admin/dormitory-records
GET /api/visitor/admin/audit-logs
```

以上为架构级初稿，正式开发前必须形成 OpenAPI 契约。

## 12. 数据所有权与数据库

初期可以共用一个数据库实例，但必须按服务进行逻辑隔离：

```text
visitor_database
├── auth_schema
├── registration_schema
├── guard_schema
├── dormitory_schema
├── oa_integration_schema
└── admin_query_schema
```

| 服务 | 数据所有权 |
|---|---|
| `auth-service` | 用户、角色、权限 |
| `visitor-registration-service` | 完整登记主数据、敏感信息、电话通知可选项及处理记录 |
| `guard-record-service` | 门卫进出状态、时间、操作人、OA审批结果只读投影 |
| `dormitory-service` | 住宿、房间、床位和调整记录 |
| `oa-integration-service` | OA流程映射、同步状态和调用日志 |
| `admin-query-service` | 综合查询投影和报表数据 |

所有服务使用 `visit_id` 建立业务关联，但不得依靠跨Schema直接写表完成业务。

## 13. 权限、安全与审计

### 13.1 权限层次

```text
前端菜单权限
→ API网关接口权限
→ 微服务业务权限
→ 数据/字段权限
```

前端隐藏菜单不等于安全控制。

### 13.2 DTO隔离

建议定义：

```text
GateVisitorVO
DormitoryVisitorVO
AdminVisitorVO
```

门卫DTO应包含 OA审批结果，但不得包含身份证、来访事由、住宿、电话结果等无权字段。

### 13.3 审计要求

至少记录：

- 二维码提交时间；
- 门卫确认入厂的操作人和时间；
- 门卫确认离场的操作人和时间；
- 床位确认、调整前后值、操作人和时间；
- 管理员修正数据的前后值及原因；
- 敏感信息查看行为（范围待确认）；
- OA/电话平台接口调用日志。

推荐形式：

## 16. 测试与验收基线

### 16.1 核心验收场景

1. 访客扫码提交完整登记，系统生成唯一 `visit_id`；
2. 每次访客登记都产生 OA审批流程；未勾选电话通知时不产生电话任务；
3. 勾选电话通知时，由登记服务内部电话通知模块创建相应任务；
4. 门卫能看到且只能看到授权字段；
5. 门卫响应中包含 OA审批结果，但不存在身份证、电话结果及其他无权字段；
6. OA审批结果为已驳回时，门卫仍能手动确认入厂；
7. 门卫确认入厂后由服务器生成时间，状态变为在厂；
8. 重复点击入厂不能产生重复有效记录；
9. 只有在厂状态才能确认离场；
10. 离场时间由服务器生成；
11. 宿舍能获取授权的完整登记业务信息；
12. 宿舍能够确认或调整床位，并保留修改记录；
13. 后台能够按权限综合查询；
14. 不同角色登录同一网站时只显示相应菜单；
15. 前端绕过菜单直接调用无权接口时，后端拒绝；
16. 访客前端能够以 `/visitor/` 子路径接入门户。

### 16.2 测试类型

- 单元测试：状态流转、字段过滤、校验规则；
- 契约测试：服务间API及事件版本；
- 集成测试：登记必走 OA审批；电话通知勾选与未勾选两种分支；
- 权限测试：角色、接口、字段；
- 幂等测试：重复提交、重复事件、重复点击；
- 安全测试：身份证、手机号、日志和接口越权；
- 用户验收测试：访客、门卫、宿舍、后台实际操作。

## 20. 最终结论

本项目最终形态为：

> 一套按角色展示不同菜单、页面和字段的统一访客管理 Web 系统；后端采用职责清晰的微服务；二维码登记服务管理主数据和可选电话通知模块，门卫服务只记录进出，宿舍服务管理住宿和床位；每次预约必须进入 OA审批流程，只有勾选时才处理电话通知；总后台提供权限化综合查询；访客系统最终作为子应用接入企业统一网站。

项目正确推进顺序为：

```text
需求确认与冻结
→ 页面和接口契约
→ 工程骨架与权限
→ 二维码登记
→ 门卫进出
→ 宿舍管理
→ OA集成和可选电话通知模块
→ 总后台
→ 企业门户接入
→ 联调、安全和验收
```

在需求未冻结之前，不进入正式业务编码。
